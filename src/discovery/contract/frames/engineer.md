# Фрейм: engineer (solution-space)

| | |
|---|---|
| Кого интервьюируем | инженер / сотрудник, знающий текущие системы и данные |
| Пространство | **solution-space** — реальность систем, ограничения, tacit-знание |
| Порождает | System Assessment (Gate 0b) + вход в Tech Selection (Gate 0a); `feeds: [system-assessment, tech-selection]` |
| Аппрувит (`owner_role`) | `architect` |

## Precondition (жёсткий)

Стартуем **только** при наличии customer-брифа со `status: approved` — прочитай его
целиком до интервью и положи ссылку в `traces_to`. Без него — стоп: иначе инженер
пересобирает требования заново и получается дубль.

## Запрет фрейма (жёсткий)

**Не пересобирать бизнес-цели и требования.** Цели/JTBD/FR берутся из approved
customer-брифа по `traces_to`. Инженера спрашиваем о реальности систем и о
реализуемости уже собранного — не «что нужно бизнесу».

## Банк вопросов по темам (каждая тема — до закрытия чек-листа)

### 1. Текущие системы и данные → `S-NN`
<!-- coverage_key: systems; produces: S -->
- Какие системы/сервисы/хранилища сейчас живут в этой области? Кто ими владеет?
- Где лежат данные, о которых идёт речь в customer-брифе? В каком виде, какого объёма,
  как часто меняются?
- Что из этого «работает, но все боятся трогать»?

Чек-лист: каждая упомянутая в customer-брифе область имеет S-запись; для каждой системы —
владелец и состояние (стабильна / хрупкая / выводится).

### 2. Интерфейсы и контракты → `IF-NN` (traces → S)
<!-- coverage_key: interfaces; produces: IF -->
- Как в эти системы попадают и как из них достаются данные (API, файлы, очереди, БД
  напрямую)? Что из этого — задокументированный контракт, а что «так исторически»?
- Какие потребители сломаются, если интерфейс изменить?

Чек-лист: у каждой затрагиваемой S-системы описаны точки входа/выхода; версионируемость
и стабильность каждого интерфейса помечены.

### 3. Ограничения инфраструктуры → `CON-NN`
<!-- coverage_key: constraints; produces: CON -->
- Что нельзя по политике: сеть, доступы, секреты, где можно/нельзя запускать код?
- Лимиты: квоты, стоимость, лицензии, поддерживаемые стеки?

Чек-лист: жёсткие «нельзя» отделены от предпочтений (предпочтения → AP); каждое CON —
проверяемый факт, не мнение.

### 4. Архитектурные предпочтения → `AP-NN` (traces → S/CON)
<!-- coverage_key: arch_preferences; produces: AP -->
- Какие подходы/стеки команда уже умеет и хочет? От чего осознанно отказались раньше и
  почему?
- Есть ли принятые ADR/стандарты, которым новое обязано следовать?

Чек-лист: у каждого AP — обоснование (почему), а не только «что»; отсылки к существующим
ADR названы.

### 5. Риски и tacit-знание → `RK-NN`
<!-- coverage_key: risks; produces: RK -->
- Что здесь ломалось раньше? Какие грабли не записаны нигде?
- Что в customer-брифе, на твой взгляд, недооценено по сложности?
- Bus-factor: что знает только один человек?

Чек-лист: ≥1 риск из личного опыта (не пересказ очевидного); недокументированное знание
явно помечено как tacit.

### 6. Feasibility-проход по customer-брифу → `X-NN` / `Q-NN`
<!-- coverage_key: feasibility_review; produces: X,Q -->
Пройди по каждому `FR-NN` (и жёстким `NFR`) approved customer-брифа:
- Реализуемо ли на текущих системах? Что «дорого/невозможно/не так, как думает заказчик»?
- Расхождение реальности с требованием → **`X-NN` с `target: FR-NN` (или G-NN),
  `status: open`** — позиция заказчика vs позиция инженера, держатели-роли.
- Нужны данные/решение, которых нет → `Q-NN` с `owner_role` и честным `blocking`.

Чек-лист: каждый Must-FR customer-брифа получил вердикт (ок / X / Q); ни один конфликт
не «усреднён» в компромиссную формулировку.

**Петля обратного потока:** каждый `X-NN` c target на customer-бриф означает, что тот
требует reconciliation — его гейт снова `false`, пока product не решит. Об этом
обязательно сказать в отчёте (Шаг 5 SKILL.md).

### Завершение (всегда)
<!-- coverage_key: none; produces: none -->
- Резюме: карта систем + главные «нельзя» + список feasibility-конфликтов — на
  подтверждение стейкхолдеру.
- «Кого ещё спросить про эти системы?» → кандидаты в sessions.

## Coverage (required-набор фрейма)

Ключи блока `coverage:` и обязательность для гейта:

| ключ | секция | гейт |
|---|---|---|
| `systems` | S | required |
| `interfaces` | IF | required |
| `constraints` | CON | required |
| `arch_preferences` | AP | required |
| `risks` | RK | required |
| `feasibility_review` | проход §6 по FR customer-брифа | required |

Опциональные секции фрейма: `P` (стейкхолдеры систем), `NFR` (инфраструктурные),
`OUT`. Инварианты присутствия: секции `Q`, `X` существуют.

## Правила извлечения

- Разделяй факт («API v2 не имеет пагинации») и мнение («лучше переписать на Rust») —
  факт → S/IF/CON, мнение → AP с обоснованием.
- Каждое IF трассируется в S; каждое AP — в S или CON.
- Ничего из целей/FR не переформулировывать — на них только ссылаться по ID из
  customer-брифа.
