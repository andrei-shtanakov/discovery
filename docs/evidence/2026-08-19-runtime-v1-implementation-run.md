## Ход прогона

### Попытка 1 (07:10–07:23) — остановлена на A1, дефект инструмента

`a1-contract` трижды прошёл `DECOMPOSING → READY → RUNNING → FAILED` и исчерпал
ретраи → `NEEDS_REVIEW`. B/C/D1 не стартовали. Полезной работы не выполнено.

Причина: `spec-runner plan --full` сгенерировал мета-строку
`🔴 **P0** | Est: **2h** | **Depends on:** … `, которую отвергает валидатор
`spec-runner run` (ожидается `🔴 P0 | ⬜ TODO | Est: 2h` — приоритет, СТАТУС,
оценка). Промпт генератора требует правильную форму (`cli_plan.py:672`) —
отклонилась модель, и результат не проверялся перед передачей исполнителю.
Заведено: **spec-runner#301** (inbox).

Почему не чинится правкой файла: ручная правка даёт `0 errors, 0 warnings`, но
установленный maestro регенерирует спеку на каждом входе в воркстрим
(«Always regenerate» в `orchestrator.py`), так что правка стирается.

Что сделано вместо: требование к формату мета-строки вписано в описание всех
четырёх воркстримов в `project.yaml` — генератор читает его вместе с заданием.
Это единственный рычаг, целиком лежащий в нашем репо.

Две сопутствующие находки, записаны в spec-runner#301: ретрай на невалидном
входе перегенерирует вместо починки (три полные генерации на одинаковый отказ),
и быстрый выход оставляет пустой `logs/<ULID>/spec-runner-<pid>.jsonl` —
диагноз возможен только ручным воспроизведением `run --all --dry-run`.

### Попытка 2 (08:12–08:26) — формат исправлен, всплыли две другие причины

Мета-строка сгенерировалась канонически (`🔴 P0 | ⬜ TODO | Est: 2h`) — рычаг
через описание работает, spec-runner принял файл и взял TASK-001 в работу.
Но воркстрим упал дважды, и обе причины другие.

**Причина A — претензия на red по уже существующему файлу.** Настоящее
сообщение исполнителя (в логах прогона его нет, добыто ручным
воспроизведением `spec-runner run --all --spec-prefix maestro-`):

```
⛔ RED not confirmed, refusing to implement: no confirmed red for this task in
this workstream — the red was written into tests/test_task_001_red.py, which
already existed before this task started. A claim freezes the whole file, so
the implementation could not add to it afterwards
```

Файл остался от попытки 1: ветка `task/task-001` **пережила удаление
worktree**, потому что ветки живут в репо, а не в рабочей копии. Снос
`ws/a1-contract` их не трогает. Урок для чистки после неудачного воркстрима:
удалять и `task/*`-ветки, иначе следующая попытка получает HOOK_FAILURE без
ретрая.

**Причина B — в репо не было `.gitignore`.** Red-коммит `0c50e58` содержит
`__pycache__/test_task_001_red.cpython-313-pytest-9.1.1.pyc` и `uv.lock`, но не
исходник теста. `.pyc` попадает в коммит и участвует в претензии на red.
Заведён `.gitignore` (`__pycache__/`, `logs/`, `spec/.executor-*`, кеши).

**Причина C — моя инструкция протекла в требования.** Формат мета-строки,
вписанный в описание воркстрима, генератор превратил в `[REQ-012] Any
downstream-generated spec/maestro-tasks.md uses the mandatory meta-line
format… Traces to TASK-001, TASK-002` — то есть в требование к
разрабатываемому рантайму, который `tasks.md` не пишет вообще (граница
author ≠ execute). Инструкция переоформлена как явная мета-инструкция
генератору с запретом заводить её как REQ/NFR/TASK.

Отдельная находка о наблюдаемости: причина A **не видна из прогона** —
`logs/<ULID>/spec-runner-<pid>.jsonl` пуст, таблицы `attempts`/`agent_calls`
состояния исполнителя пусты, в БД maestro только «spec-runner exited with
code 1». Диагноз потребовал ручного воспроизведения в worktree.

### Попытка 3 (08:29–08:35) — прошла дальше всех, вскрыла дефект плана

Две прошлые причины не воспроизвелись: мета-строка каноническая, red-фаза честная —
коммит `e400393` с настоящим тестом на 42 строки, без `.pyc`. Тест прогнан вручную:
падает по assertion об отсутствующем поведении, а не по ImportError, то есть red
законный.

**Причина D — дефект плана, а не инструмента.** `Task 1 Step 3` предписывал
`uv run tools/vendor_pull.py ../discovery-toolkit`. Из worktree
`discovery-maestro-ws/a1-contract/` путь `../discovery-toolkit` не существует: рядом
лежит только сам worktree, а upstream-чекаут — в `~/labs/all_ai_orchestrators/`.
Шаг писался из основного чекаута, где сосед действительно рядом. TASK-001 был
невыполним в принципе.

Что именно этот шаг оборвал конкретный прогон — не доказано (лог фазы реализации снова
пуст), но недостижимость upstream доказана и достаточна.

**Исправление: пред-вендоринг.** Копия контракта и линтера положена на базовую ветку
руками, байты взяты `git show <commit>:<path>` из **дерева коммита**, а не из рабочей
копии соседа — иначе провенанс не гарантирован. Обе сверки совпали. TASK-001 теперь
пишет `tools/vendor_pull.py` и тестирует его **герметично** против поддельного upstream
в `tmp_path`; ни одна задача больше ничего не требует снаружи своего worktree. Тот же
приём заранее чинит TASK-014 (банк), который уткнулся бы в тот же путь.

### Попытка 4 — с пред-вендоренной копией

Запущена с изолированной БД `~/.maestro/discovery.db`: первая попытка шла в

08.08 (строки `tasks` целы). Установленный maestro 0.4.0 держит одну БД на все
проекты; per-project раскладка есть только в свежих исходниках.
